# Workspace-local kernel-isolated runtime

The restarted Workspace host's actual LSM chain omits BPF, so native block cannot be evaluated there. These scripts provision an official Debian cloud image inside the existing Workspace through KVM. They change no host boot parameter or kernel. The official task files, model, harness defaults, policy compiler and engine remain unchanged; the expanded cohort records a separate runtime stratum.

The immutable setup-only template and worker configuration are recorded in [workers-launch.csv](results/workers-launch.csv) and [template.json](results/template.json). Each task's complete condition sequence stays on its assigned worker. Every worker uses a conservative one-enforcing-loader rule to keep parallel measurements unambiguous. An initial source-only concern about overlapping loaders did not establish interference: kernel trampoline return handling must also be considered. Any composition control is separate from official task outcomes. Metadata CSVs are written by the sole host coordinator; shared-filesystem locking across kernels is not assumed.

Actual kernel, boot identity, active LSM chain, mounts and matching engine/compiler hashes are recorded separately for [worker one](results/worker1-environment.csv), [worker two](results/worker2-environment.csv) and [worker three](results/worker3-environment.csv). Native zero-seed denial controls and the official harness setup-only root/strace preflight are separate admission evidence owned by the expanded benchmark runner. Capability metadata does not count as benchmark success or false-intervention evidence.

The cloud base image is downloaded from the [official Debian cloud repository](https://cloud.debian.org/images/cloud/trixie/latest/) and checked against its published checksum; [image.json](results/image.json) records exact bytes and source. The cloud kernel lacks the shared-filesystem transport. A setup-only failed boot was preserved remotely, then the official full kernel was installed and selected before any benchmark model ran. Shared mounts use `nofail` during provisioning. A second setup-only repair preserved failed worker boot logs and reused the template NIC MAC on independent user-network backends so the persisted cloud network configuration applies.

From the synced lane source directory, `bootstrap.py` creates the setup guest, `configure_docker.py` configures its empty guest-local daemon, and `clone_workers.py` cleanly freezes the fully provisioned guest and starts isolated worker kernels. They refuse to modify active benchmark runtimes. `probe_guest.py --worker N` verifies actual capability and tool identity, and `publish_metadata.py` exports these small facts. The native task runner handles per-worker controls, image inventories, credentials passed through private runtime channels and official trials. Do not rerun bootstrap or repair scripts against healthy model jobs.

The original guest disks and image layers were rebuildable under the Workspace's temporary filesystem. Cited traces, source proofs, manifests and logs remain in the durable lane directory. Full serial and failed-boot logs are retained remotely; only small JSON/CSV metadata are committed. Guest Docker sockets and container storage stay local to each guest, while the lane is shared read/write and the previous translation tools are mounted read-only. No host daemon socket is rebound.

The original worker epoch ended in a confirmed node-wide OOM. The kernel selected a QEMU process and the Workspace's group-OOM setting killed the remaining processes, including all workers and the coordinator. The container restarted without a host reboot, losing its temporary disks and key. The actual host and shared Kubernetes memory ceiling were much smaller than the supplied hardware description. `diagnose_reset.py` retains the kernel log, own-cgroup ancestry, host memory and reset evidence under durable `raw/benchmark/expanded/vm/reset-20261029T1954`; no service-account token was available to independently fetch Kubernetes termination status.

Recovery uses a single bounded guest, with complete task condition sequences run sequentially. `recover_small.sh` and `bootstrap.py` check actual available memory before launch. `freeze_recovery.py` saves a clean, independently restorable golden image to the durable lane with a disk-use guard, then launches the recovery worker. The private recovery SSH key stays in a restricted remote runtime directory and is never exported. The original multi-worker constructor is historical and is not the recovery entry point. Old capability receipts, failed model-transport attempts and new recovery receipts remain separate; the benchmark runner must revalidate controls, setup and transport before admitting the new epoch.

The [reset summary](results/recovery-20261029T2005/reset-summary.csv) records the original aggregate allocation and the measured host memory. The [recovery launch](results/recovery-20261029T2005/workers-launch.csv) uses one 8 GiB guest with 8 vCPUs; the official native task limits remain unchanged. The [recovery environment](results/recovery-20261029T2005/worker1-environment.csv) records its distinct boot ID, active BPF LSM, full kernel, actual guest memory, read-only tools mount and engine/compiler identity. The [standalone template receipt](results/recovery-20261029T2005/template.json) records the durable golden image's hash and confirms it has no ephemeral backing file. These are infrastructure facts, not additional valid task outcomes.
